## Turn on the public controls after approval

1. Publish an ordinary PR from a branch. Run Validate and CodeQL with no repository secrets and confirm the actual job contexts and integration identity from the check runs. Compare against the draft ruleset. Use GitHub Actions as the expected source for each required check. Verify the dependency graph, Actions permissions, repository visibility, and CodeQL setup in the owner view first.
2. Exercise a passing change and a synthetic violation before making the checks required. A stale review block must fail **App and Pages checks**, and an introduced dependency with a high or critical advisory must fail **Dependency review**. Run the tests without merging the failing contributions. Confirm the code scanning result appears under Security and includes the expected source paths.
3. Activate the main ruleset with no bypass actors after checking the actual default branch and check contexts. The draft requires a PR and resolution of review conversations, with zero mandatory approvals pending confirmation of an independent reviewer. Once that reviewer is available, require one approval and enable last-push approval. Recheck that an ordinary passing PR can merge and an unresolved or failing PR cannot.
4. Tighten the Pages environment after confirming the active source and rollback path. After an authorized merge and successful Pages deploy, dispatch **Verify publication** on `main`. Record the deployed commit, both job conclusions, and the matching digests. It uses the existing deploy path. Update `wiki-source/` in the same PR as future documentation edits, and sync the separate Wiki after review.
5. Verify the owner-only security settings and project membership. After approval, link the existing owner Project or create one if needed and add the GitHub topics. Add the next implementation and platform milestones only when there are approved issues to place in them. Keep Q&A and ideas separate from bug reports when Discussions has moderation coverage.
6. Qualify distribution separately. For a future release, use a clean source checkout and verify the staged ZIP against the approved digest and both Civitai catalogs. Duplicate the build, verify its entries, and verify the final archive digest using the pinned packaging path before using a build-provenance attestation. Keep signing and release permissions on an explicit release job. On publish, verify the immutable release and downloaded asset. There is no GitHub release job in this review.

## Cost boundary

The new workflows target only the public repository's standard `ubuntu-24.04` runners. Their jobs require the event to identify a public repository. The workflows use free public Pages and public repository security features, with no user-configured Actions cache, artifact uploads, larger runners, paid plan, or new metered service. CodeQL submits SARIF to code scanning and disables database uploads. GitHub may report free allowances for other products. Use a metered product only after verifying an applicable budget configured to stop usage at $0. The owner billing view was unavailable in this review.
